# X5 Чекпоинт — финальный план и спецификация продукта

**Обновление 07.09.2026:** Коробка выдаётся за три разных дня входа по Москве, максимум четыре за последние 28 дней. Пропуски не сбрасывают прогресс; первый показ счётчика резервирует 25 ₽, открытие переносит этот резерв предмету. Новые купоны — до 100 ₽, прежние проценты и рецепты сохранены.

**Актуальность:** 07.09.2026. **Слоган:** «Собирай свою выгоду».
**Статус:** интерактивная игра и локальный персональный PoC образуют один демонстрационный путь. Коробка даёт случайный предмет, персональное задание проходит путь «синтетическая история → rules-based задание → локальный Ads-аукцион → проверенная карточка → тестовый чек → окно обещанной награды и одноразовый CPA-биллинг», и обе награды попадают в одну коллекцию, из которой четыре предмета собираются в демо-скидку. Отдельно реализован offline learned RecSys на рандомизированной синтетике. Реальная выдача, POS, защищённый backend, production bidder accounts и обучение на данных X5 остаются следующим этапом.

Требования задаёт [описание кейса и Q&A](case-brief.md), реализацию — код и проверки. Документ объединяет существующую игру команды и финальный план её развития: игровые правила, пользовательские сценарии, персонализацию, финансирование, обмен, защиту и критерии приёмки. Полный каталог предметов и состав рецептов включены в приложение А; порядок реализации и ответственность — в [плане команды](plan.md).

Компактные Markdown-материалы в `docs/presentation/` представляют решение по требованиям финальной сдачи; полная спецификация остаётся здесь. Неактуализированные v4/v5 не задают продуктовые правила. Фактическую готовность определяют текущий код, локальные проверки и [статус PoC](poc-status.md).

## 1. Продукт и пользователь

**X5 Чекпоинт** связывает обычные покупки с понятной выбранной наградой. Покупатель собирает цифровые кухонные предметы, выполняет посильные персональные задания и обменивает дубликаты. Четыре предмета уже позволяют создать скидку в прототипе. В целевой версии для части рецептов появляется второй результат — конкретный бесплатный товар из заранее обеспеченного каталога. Например, цель «Доброе утро» может обещать выбранный йогурт: пользователь видит сам товар, недостающие предметы и следующий шаг.

Первый целевой сегмент для проверки — совершеннолетние пользователи приложения «Пятёрочки» из сегмента молодёжи с нерегулярными покупками привычных категорий. Это выбранная продуктовая гипотеза. В Q&A молодёжь составляет 37% аудитории приложения сети; это обоснование размера сегмента, а интерес к коллекции ещё нужно проверить на людях.

Вторая роль — продакт или маркетолог X5: экран «Для X5» показывает объяснение решения, финансирование и результаты сравнения политик. Для следующего промышленного контура нужны также контроль риска и исполнения обязательств. Бренд выступает участником финансирования; отдельный рекламный кабинет не нужен для основного покупательского демо.

## 2. Почему этот вариант отвечает кейсу

Кейсодатель объясняет слабые результаты прошлых игр длинным путём до награды и низкой ценностью приза. Поэтому целевой первый челлендж заканчивается после **одного обычного допустимого покупочного дня**, с заранее известными условиями и наградой. «Первое задание» не должно скрывать пять визитов или большой обязательный чек.

После выполнения первого показанного допустимого задания пользователь гарантированно получает **полный бесплатный физический товар и полезный цифровой предмет**. Затем бесплатный товар остаётся возможной видимой целью следующих циклов: у обеспеченного рецепта заранее показаны конкретный SKU, условия и прогресс. Предметы выдаются за следующие задания и могут обмениваться. Четыре копии используются на один выбранный результат — обычную скидку либо товар по активной обеспеченной цели. Подарок не положен за каждое задание или любой рецепт: доступность и частоту определяют финансирование, наличие, риск и консервативная экономика. Правило «после первого раза в основном только скидки» больше не задаёт развитие продукта.

Q&A допускает продукт без ML-модели внутри. На защите всё равно нужно показать фактическое использование конкретных ИИ-инструментов в разработке и продуктовом исследовании. В runtime используется объяснимый выбор по правилам, а обучаемая версия предъявляется как отдельный проверенный offline-контур на синтетических логах, без подмены этим реального эффекта X5.

## 3. Что уже работает

Исходная игровая механика сохраняет поведение коллег. Персональный PoC описан сразу после таблицы; его награды и предметы из коробки за входы лежат в одной коллекции и расходуются одним крафтом.

| Компонент | Фактическое состояние |
| --- | --- |
| Игровой профиль | Персонаж, коробка, анимация открытия движением пальца/указателя по экрану |
| Каталог | 24 цифровых предмета, три редкости, семь тематических рецептов |
| Коробка | Безлимитный демонстрационный режим; случайная редкость с весами 70% / 25% / 5% |
| Инвентарь | Получение предметов, накопление копий, карточки с игровыми намёками |
| Создание скидки | Четыре копии расходуются; редкость и совпадения с рецептом определяют процент; достижимый максимум текущего каталога — 17%, программный потолок — 18% |
| Состояние | Инвентарь и одна активная скидка в браузерном `localStorage`; новая скидка заменяет предыдущую |
| Штрихкод | Демонстрационный EAN-13 с корректной структурой; реальное кассовое погашение отсутствует |
| Задания | Четыре статические карточки; покупка не обновляет их прогресс |
| `recsys/` | Python-движок решения и проверки чека, адаптер Qwen/fallback, синтетическая оценка; прежние allocator-фикстуры проверяются отдельно |

Источники реализации: [экран профиля](../../webapp/src/features/home/ProfileScreen.tsx), [карточка задания](../../webapp/src/features/home/DemoQuestSection.tsx), [состояние персонального сценария](../../webapp/src/features/home/use-demo-challenge.ts), [предметы](../../webapp/src/features/home/profile-items.ts), [создание скидки](../../webapp/src/features/home/profile-discount-crafting.ts) и [движок выбора](../../recsys/engine/decision.py). Подсказка ближайшего рецепта остаётся игровым правилом; задание рассчитывается движком по синтетической истории и общему инвентарю.

Vite middleware передаёт contract v2 локальному Python-движку. Он выбирает задание, проводит quality-adjusted first-price CPA-аукцион, проверяет чек, риск и идемпотентность; браузер одним снимком хранит обещание, награды, фонды, Ads-бюджеты, показы и биллинги. Первый физический подарок возможен только с победившей рекламной кампанией, `bid + subsidy` резервируются до показа, а списание происходит ровно один раз после свежего `qualified + allow` события. Право на SKU и рекламный ledger остаются демонстрационными: POS и защищённого серверного реестра нет. Обмен выполняется локально между синтетическими профилями. Персональная выдача и случайная коллекция используют разные состояния браузера; экран не позволяет потратить выданный челленджем предмет в слотах основной коллекции. Работоспособность PoC не доказывает экономику реальной программы.

### 3.1. Коробка, предметы и инвентарь

Коробка остаётся узнаваемым действием игры: пользователь проводит пальцем или указателем по экрану, коробка встряхивается и раскрывает результат. Это экранный жест, не показания акселерометра. Коробка выдаётся за три разных дня входа по Москве, максимум четыре за последние 28 дней. Пропуски не сбрасывают прогресс; первый показ счётчика резервирует 25 ₽, открытие переносит этот резерв предмету. После анимации предмет уже начислен; кнопка «Забрать» закрывает результат, а не запускает вторую выдачу.

У каждого из 24 предметов есть постоянный ID, название, редкость, изображение, товарная ассоциация и описание-загадка. В каждой редкости восемь предметов. Случайная коробка сначала выбирает редкость с вероятностями 70% / 25% / 5%, затем равномерно выбирает предмет этой редкости. Повторы допустимы, защиты от дубликатов нет. Вероятности относятся к нынешней случайной коробке; будущая коробка по выполненному заданию раскрывает заранее назначенный предмет.

Дубликат увеличивает число копий, не создаёт новый вид предмета. Счётчик коллекции показывает разные предметы, которые сейчас есть в инвентаре, из 24; после расхода последней копии он может уменьшиться. Карточка инвентаря показывает название, редкость и загадку. Категория явно раскрывается на экране получения и в готовом предварительном расчёте скидки. Не обещаем, что она скрыта во всём интерфейсе.

Пользователь открывает карточку, выбирает предмет и слот либо перетаскивает предмет. Слотов четыре. В них можно положить несколько копий одного ID, если их достаточно. До создания скидки копии лишь заняты в интерфейсе; их можно убрать или заменить. При создании расходуется ровно четыре копии. Существующая подсказка выбирает ближайший рецепт по совпадениям и предлагает недостающие ID из каталога; она не учитывает историю покупок и наличие подсказанного предмета в инвентаре.

### 3.2. Рецепты и расчёт собственной скидки

Рецепт — список из 5–7 подходящих предметов, из которого можно собрать разные сочетания. Семь направлений: «Доброе утро», «Свежий выбор», «Вечер без готовки», «Азиатский ужин», «Ужин шефа», «Сладкая пауза», «Домашний запас». Полные составы, категории, ID и загадки — в приложении А и [каталоге игры](item-pool.md).

Каждая обычная копия даёт одно очко силы, эпическая — два, легендарная — три. Сила четырёх выбранных копий определяет базовую скидку:

| Сумма силы | Базовая скидка |
| --- | --- |
| 4–5 | 5% |
| 6–7 | 7% |
| 8–9 | 10% |
| 10–11 | 13% |
| 12 | 15% |

Выбирается рецепт с наибольшим числом **разных** подходящих ID. Три разных совпадения добавляют 2 процентных пункта, четыре — 3. Бонусы разных рецептов не складываются. При равенстве числа совпадений действует порядок семи рецептов, указанный выше. Если нет трёх совпадений, бонуса нет, а категория берётся у самого редкого выбранного предмета; при равной редкости — у первого по порядку слотов.

Редкость результата определяется отдельно: сила 4–6 — обычная скидка, 7–9 — эпическая, 10–12 — легендарная. Формула ограничивает результат 18%, но текущие составы рецептов позволяют получить максимум **17%**: четырёх разных легендарных предметов в одном рецепте нет.

| Выбранные четыре копии | Результат по существующим правилам |
| --- | --- |
| Клубный тостер + Молочный кувшин + Термокружка + Сковорода завтрака | 4 очка, база 5% и бонус 3 п.п. → «Доброе утро», 8% |
| Фруктовая корзинка + Овощной ящик + Блендер здоровья + Купол свежести | 7 очков, база 7% и бонус 3 п.п. → «Свежий выбор», 10% |
| Золотой колпак повара ×2 + Волшебный холодильник + Королевский казан | 12 очков, три разных совпадения → «Ужин шефа», 17% |
| Фруктовая корзинка ×4 | 4 очка, один разный ID → 5% на фрукты без бонуса рецепта |

### 3.3. Результат и переход к защищённому учёту

После создания показываются процент, категория, использованные предметы и демонстрационный EAN-13; значок скидки появляется рядом с персонажем. Сейчас инвентарь и одна активная скидка сохраняются отдельно в браузере. Новая скидка заменяет прежнюю. Штрихкод имеет контрольную цифру, но не зарегистрирован на кассе; срока действия и реального погашения нет.

В целевой версии сервер хранит экземпляры предметов, обещания и купоны. Процент и применимые товары рассчитываются из версии рецепта на сервере. При выдаче фиксируются срок, рублёвый максимум, область применимости и совместимость с промо. Чтобы сохранить уже заработанное право, **новый крафт скидки недоступен до погашения или истечения действующего купона**; это выбранное правило следующей реализации, отличающееся от текущей замены в демо. Предметы можно продолжать получать и обменивать. Изменение каталога не переписывает условия уже выданной награды.

## 4. Целевой игровой цикл

Сохраняется цикл коллег: **коробка → цифровой предмет → инвентарь → четыре предмета → собственная скидка → штрихкод**.

К нему подключается последовательность:

1. История привычных категорий, ритм визитов и инвентарь задают контекст.
2. Система выбирает одно выполнимое задание, полезное для выбранного или ближайшего рецепта.
3. До показа проверяются риск, наличие SKU, финансирование и полная максимальная стоимость обязательств.
4. Покупатель видит условие, срок, конкретную награду и маркировку спонсорства, если оно есть.
5. Подтверждённая покупка однократно засчитывает выполнение. Коробка раскрывает обещанный предмет; случайное выпадение не заменяет обещание.
6. После первого такого челленджа выдаётся право получить обещанный полный физический товар бесплатно. Новая платная покупка для получения уже заработанного товара не требуется.
7. Пользователь пополняет коллекцию, при необходимости обменивает дубликат и использует четыре предмета для скидки либо для конкретного товара по активной обеспеченной цели рецепта. Следующая награда видна до прохождения соответствующего цикла.

`no_action` применяется до нового обещания. Уже заработанный инвентарь, действующие награды и резервы сохраняются. Если подходящего спонсора нет, допустим обычный челлендж; если нет полезного и экономически допустимого задания, новое задание не выдаётся. Первый бесплатный товар не является бонусом за регистрацию и не обещается каждому без проверки.

**Два профиля персонального PoC.** У нового пользователя А инвентарь пуст: первый показанный и выполненный допустимый челлендж записывает демонстрационное право на упаковку овсяных хлопьев и один полезный цифровой предмет. У демонстрационного пользователя Б заранее заданы три обычных предмета — Клубный тостер, Молочный кувшин и Термокружка; это явно подготовленное состояние, не бонус регистрации. За один следующий допустимый покупочный день ему обещана Сковорода завтрака (`breakfast-pan`). После выдачи она попадает в ту же коллекцию и позволяет через пользовательский интерфейс завершить «Доброе утро» со скидкой 8%. Семь дней — параметр примера, не обязательный срок для всех.

Конкретный физический SKU, упаковка, место и срок получения задаются каталогом до показа. Наличие и стоимость в примере синтетические. Полезность товара должна быть подтверждена пользовательской проверкой; название «бесплатный» само по себе её не гарантирует.

**Квалификация покупки в локальном PoC:** до показа задание фиксирует допустимые SKU или категорию, минимальное количество оплаченных единиц и срок. Синтетический демонстрационный вариант — одна оплаченная единица из указанной в задании категории за семь дней после показа. В примере «Доброе утро» можно указать молочные продукты; покупка из другой категории условие не закрывает. Бесплатная строка, повторный чек и повторное событие не начисляют награду. Один подтверждённый покупочный день учитывается один раз. Возвраты передаются в отдельную проверку и не становятся новым основанием начисления. Эти значения — настройка демо, а не универсальные условия X5; достаточность экономики и риска проверяется независимо от выполнения товарного условия.

### 4.1. Что видит пользователь на каждом шаге

Для локального PoC достаточно профиля с заданием и раскрытием награды, инвентаря с рецептом, результата/купона и диагностического разбора. Локальный обмен имеет свой интерфейс: предложение, резерв копий и принятие второй стороной; повторная товарная цель остаётся следующим слоем.

| Экран / состояние | Содержание и действие | Правило и статус |
| --- | --- | --- |
| Профиль | Персонаж, коллекция, активная скидка, конкретная товарная цель при её наличии и один следующий челлендж | Доступ к заработанным предметам остаётся и без нового задания |
| Карточка челленджа | Одно действие, срок с часовым поясом, конкретные предмет и SKU, место/срок получения, причина выбора, спонсор | Условия фиксируются при показе; нет скрытой необходимости второй покупки |
| Проверка события | «Покупка получена», затем результат проверки или понятная причина удержания | Повторная отправка того же чека не начисляет награду повторно |
| Результат | Та же коробка раскрывает обещанный предмет; рядом отдельное право на бесплатный товар | Открытие/закрытие анимации не влияет на факт выдачи |
| Инвентарь и рецепт | Имеющиеся копии, недостающие ID, выбор четырёх копий, предварительный расчёт | Доступное количество исключает зарезервированные для обмена копии |
| Обмен | Свой доступный предмет, запрошенный предмет той же редкости, срок и подтверждения | Резерв и передача контролируются сервером |
| Скидка | Процент, товары, рублёвый предел, срок, код и статус | Один активный купон; заработанное право не заменяется новым крафтом |
| Разбор для продакта | Профиль без персональных данных, кандидаты, причины отказа, стоимость, резерв, риск, события | Диагностика решения работает в персональной панели; отдельный кабинет бренда не требуется |

### 4.2. Состояния задания и двух наград

Локальный снимок хранит связь решения, показанного задания, квалифицирующего события и **двух независимых наград**. Таблица также фиксирует целевые серверные состояния получения товара и истечения, которых в браузерном PoC нет.

| Объект | Переходы | Инвариант |
| --- | --- | --- |
| Задание | Допущено и обеспечено → показано → событие получено → выполнено; либо истекло без выполнения | До показа нет пользовательского обещания; после показа нельзя менять условие и приз |
| Проверка | Разрешено / дополнительная проверка / удержано / отклонено | Удержание сохраняет резерв; отказ содержит причину и путь пересмотра |
| Цифровая награда | Обещана → выдана → доступна → зарезервирована для обмена или потрачена в крафте | Один источник выдачи, одна копия, нет двойного расхода |
| Физическая награда | Обещана → право выдано → получена; либо истёк заранее показанный срок | Покупка и бесплатная выдача — разные события; для получения не нужен новый платный чек |
| Купон | Создан → активен → погашен либо истёк | Сервер списывает четыре доступные копии и создаёт купон в одной транзакции |

Закрытие кампании или отсутствие нового рекламного бюджета не снимает прежнее обещание. Если товар стал недоступен после показа, право и резерв сохраняются, случайная замена запрещена; оператор организует исполнение исходного обещания либо предлагает равнозначный вариант с согласием пользователя. Возврат покупки проходит заранее определённую проверку: автоматическое удаление уже заработанных предметов или чужих предметов после обмена не допускается. Невозмещаемая потеря отражается в экономике и сигнале риска.

### 4.3. Минимальный каталог заданий

Первый тип — один подтверждённый покупочный день в заданном окне, без требования резко увеличить корзину. Повторные задания используют тот же принцип: знакомая категория либо осторожное исследование близкой разрешённой категории, нужный цифровой предмет и посильный срок. Задание с оплатой брендом может квалифицировать конкретный оплаченный SKU; платное условие и бесплатная награда явно разделены. Покупка уже выданного бесплатного товара за ноль рублей не считается платным повтором.

Кандидат содержит действие, окно, целевой рецепт, недостающий предмет, физическую награду при допустимости, наличие, маржу, источник средств, условия рекламной оплаты и полную ответственность. Для малого каталога все кандидаты оцениваются. Пользователь может выбрать интересующий рецепт; без явного выбора применяются история категорий и текущие разные предметы. Порядок кандидатов RecSys задаётся полезностью и экономикой, затем стабильным ID кандидата по плану RecSys. Порядок рецептов каталога разрешает только ничьи существующего игрового крафта и подсказки.

### 4.4. Видимая товарная цель повторного цикла

Это расширение будущей выдачи наград; существующие 24 предмета, семь составов рецептов и формула скидки сохраняются. Физический товар не выводится из изображения цифрового предмета: цифровой тостер не обещает бытовую технику. Товар задаётся отдельным разрешённым SKU кампании или каталога X5.

| Правило | Поведение следующей реализации |
| --- | --- |
| Видимая цель | Одна активная товарная цель на пользователя. До показа обещания проверены наличие и полный резерв. Карточка содержит рецепт, конкретный SKU/упаковку и количество, условия завершения, срок с часовым поясом, место/срок получения и спонсора при его наличии |
| Выбор | Пользователь выбирает интересующую доступную цель; RecSys рекомендует подходящую и следующее посильное задание. Нельзя заменить выбранный товар другим без согласия |
| Прогресс | Показаны имеющиеся и недостающие предметы. Товарная цель засчитывается по четырём доступным копиям, для которых существующий алгоритм определяет именно целевой тематический рецепт с бонусом; четыре одинаковые копии не считаются завершением тематической цели |
| Один результат за четыре копии | Пользователь подтверждает: обычная скидка по существующей формуле **либо** один обещанный физический товар. Одни и те же копии не дают оба результата. Расход четырёх копий и создание права на товар атомарны |
| Обмен помогает цели | Допущенные к обмену копии могут завершить рецепт; сам обмен не выдаёт новый физический товар. Товарная цель и право на SKU не передаются другому пользователю |
| Активная скидка | Блокирует только создание нового купона до погашения/истечения. Получение товара по отдельной активной цели не заменяет действующую скидку |
| Повторение | После закрытия цели может быть предложена следующая обеспеченная цель. Лимиты частоты и получений задаются заранее; бесконечное получение товара за одни предметы исключено |
| Нет подходящего товара | До нового обещания доступен обычный путь к скидке с понятной категорией и условиями. Если нет полезного допустимого задания, применяется `no_action`. Уже показанная товарная цель сохраняется |

**Пример повторного цикла.** У участника уже был первый подарок. Теперь он выбирает «Доброе утро — один йогурт из доступного каталога». Конкретные SKU, упаковка и срок закреплены в обещании; «йогурт» здесь лишь иллюстрация безопасного товара. Задания дают недостающие цифровые предметы, а допустимый обмен может ускорить сбор. Тостер, кувшин, термокружка и сковорода позволяют потратить четыре копии на обещанный товар. Если пользователь использует их для обычного крафта, он получает существующие 8% и теряет эти четыре копии; товар за них автоматически не выдаётся.

Товарная цель — отдельное обязательство со своей историей: **обеспечена и показана → выполняется → четыре копии списаны и право выдано → товар получен**. Возможны явный отказ пользователя или истечение заранее показанного срока. Создание обычной скидки не отменяет цель автоматически и не освобождает её резерв; прогресс пересчитывается по оставшимся копиям. Цель закрывается однократно, повтор запроса возвращает прежнее право. Изменение доступности после обещания не позволяет молча заменить подарок или удалить прогресс.

Первый физический подарок по заданию остаётся отдельным от результата рецепта: для него не требуется списывать четыре предмета. Если одному пользователю одновременно обещаны первый подарок и товар за рецепт, учитываются **два** физических обязательства и их совместная экономика. Одно событие не создаёт незапланированное повторное начисление или второй CPA-платёж.

### Почему игра может поддержать возвращение

Рабочая гипотеза: знакомая потребность в продуктах напоминает о выбранном конкретном результате; посильное задание связывает следующую обычную покупку с прогрессом; пользователь выбирает сочетание и может обменять дубликат. Конкретный товар или понятная скидка дают смысл завершению. Мы проверяем, помогает ли этот опыт повторно выбрать X5 в обычной покупочной ситуации.

Возвращение за подарком не равно устойчивой покупке без новой награды. Самостоятельный вклад игры пока не доказан: проверяем ту же конкретную награду с теми же условиями и сроками с коллекцией и без неё. После заранее заданного окна игровых поощрений отдельно наблюдаем **платные** покупки без новых целевых подарков и дополнительных игровых скидок; ранее выданные права сохраняются. Обычные промо сети сопоставимы между группами. Период оценки покупок без игровой выгоды задаётся после предусмотренных сроков выполнения и погашения. Если в наблюдении ещё действуют игровые награды, результат называется повторными покупками при оставшихся поощрениях, а не устойчивостью без них. Открытия коробки, получение SKU и даже одна платная покупка не доказывают сформированную привычку.

## 5. Социальные правила, безопасность и антифрод

### 5.1. Прямой обмен цифровыми предметами

**Локальная приёмка:** «Аня · обмен» предлагает кувшин за сковороду; «Борис · обмен» принимает, после чего Аня собирает «Доброе утро» на 8%. Оба профиля подготовлены с нужными предметами и двумя синтетическими покупочными днями. Создание предложения означает согласие отправителя, принятие — согласие получателя. Предметы резервируются, недоступны крафту и передаются одним локальным обновлением; срок — 24 часа, лимит — три завершённых обмена за последние семь дней. Перезагрузка, принятие, отклонение и последующий крафт проверены браузерными сценариями. Серверная защита и общая торговая площадка не заявляются.

Первая социальная версия — обмен любыми имеющимися и свободными цифровыми предметами между двумя пользователями:

- один предмет на один предмет той же редкости;
- разрешено предложить единственную копию предмета;
- предложение действует 24 часа, обе стороны подтверждают обмен;
- предметы резервируются; передача обеих сторон выполняется атомарно;
- не более трёх завершённых обменов в неделю для каждого участника;
- у каждого участника минимум два подтверждённых покупочных дня;
- физические товары, купоны, активные скидки и ещё не полученные награды не передаются.

Отмена, истечение срока или отказ снимают резервирование предмета для обмена; его купонное обеспечение сохраняется. Повторное подтверждение не создаёт вторую передачу. Обмен не начисляет новый бонус. Одинаковая редкость не означает одинаковую стоимость: более удачные сочетания повышают вероятность создания и погашения скидки. До подтверждения проверяется покрытие совокупных обязательств после обмена.

Аукцион предметов и обмен на деньги не входят в первую версию. Аукционный слой относится к конкуренции рекламодателей за подходящий челлендж.

### 5.2. Отдельный контур антифрода

| Риск | Что проверяем в целевой версии |
| --- | --- |
| Повторный чек или запрос | Уникальность чека, события выполнения, начисления и погашения; идемпотентный повтор возвращает прежний результат |
| Дробление корзины | Покупочный день считается один раз; несколько чеков не дают несколько первых наград |
| Аномальная скорость | Частота выдач, подтверждений, погашений и обменов в окнах времени |
| Возврат после награды | Связь исходной покупки, возврата и выданной награды; удержание до проверки по заранее показанным условиям |
| Мультиаккаунты и саморефералы | Общие платёжные инструменты, связи аккаунтов, повторяемость действий и источники предметов |
| Циклические обмены | Повторяющиеся цепочки, круговой возврат предметов, попытки передать награду из удержанного события |
| Легитимная семья | Общий телефон или устройство — только признак; самостоятельно он не вызывает блокировку |

Результаты проверки: **разрешено**, **дополнительная проверка**, **удержано**, **отклонено**. Причина и версия правил сохраняются. Неопределённый риск ведёт к проверке или удержанию; жёсткий отказ требует объяснимого основания. Порог выбирается по ожидаемому ущербу и цене ошибочной блокировки, с приоритетом precision.

Сервер должен владеть выдачей, резервом, списанием и переходами состояний. Браузерное состояние текущего демо не является защищённым реестром. Для PoC достаточно воспроизводимого локального скоринга синтетических событий; промышленный антифрод и кассовая интеграция исключены кейсом.

Проверочный набор должен содержать и атаки, и обычные покупки, и семьи с общим устройством. Отдельно показываются precision, recall, доля удержаний, ложные отказы и стоимость ошибок. Текстовый валидатор креативов эти проверки не заменяет.

### 5.3. Товарные и социальные ограничения

Алкоголь, табак, никотин и другие чувствительные категории исключены из PoC. Отсутствие прошлых покупок не используется для стимулирования потребления таких товаров. Возможное будущее рассмотрение потребует отдельной юридической оценки, возрастной проверки и политики ответственного продвижения; это не обещание допустимости запуска.

Интернет-реклама алкоголя ограничена статьёй 21 закона «О рекламе»; для актуального обоснования используем [текст закона](https://www.consultant.ru/document/cons_doc_LAW_58968/e4311f6720a4a4457f53bce4382af75b7858054e/) и [руководство ФАС](https://www.consultant.ru/document/cons_doc_LAW_478673/7655e692d8266ad2c58af5ab0aca1cac706aacf6/). Письмо ФАС 2012 года из раннего плана помечено источником как утратившее силу и не используется как действующее основание.

Сумма чека напрямую не повышает уровень аватара и не увеличивает награду линейно. Экономия — подтверждённая выгода при погашении в рублях; номинал скидки и стоимость инвентаря ею не считаются. Рейтинг, если показывается, добровольный, с псевдонимами и без ФИО/адресов; он не определяет ценность награды.

Обмен не заменяет реферальную программу. В локальном PoC расчёт `family_relay` выдаёт один обычный предмет пригласившему только после разрешённой квалифицирующей покупки нового участника, при свободных 25 ₽ резерва и без повторного начисления. Рейтинг сравнивает друзей по числу собранных наборов и предметов; погашенная экономия за 28 дней остаётся личной цифрой в шапке. Оба правила работают на синтетических событиях, а экранный seed показывает связь Ани и Бориса. Промышленная кампания приглашений не подключена. `store_coop` — дальнейшее расширение.

### 5.4. Личный прогресс, аватар, рейтинг и реферал

Для пунктов кейса используется следующая конкретизация. Расчёты работают в локальном персональном PoC; промышленный учёт остаётся будущим. Внешность маскота уже меняется: принадлежащие пользователю фартук пекаря и нож шефа можно надеть по отдельности или вместе, и это не влияет на скидку.

**Личный прогресс:** число разных завершённых рецептов от 0 до 7, отдельное от наличия предметов в инвентаре. Повторный крафт того же рецепта не увеличивает этот счётчик. У персонажа отображается освоенный рецепт и прогресс; оформление остаётся в существующем визуальном стиле. Сумма чека напрямую не повышает уровень аватара. Расход предметов не обнуляет историю завершённых рецептов.

**Рейтинг:** сравнение только с друзьями и только по собранным наборам и предметам. Деньги в сравнение не выносятся: соревнование по тратам или сэкономленным рублям подталкивало бы покупать больше, поэтому суммы остаются личной цифрой в шапке профиля. Равный прогресс даёт одинаковое место; стабильный ID задаёт только порядок вывода. ФИО, адреса и стоимость предметов в рейтинг не входят, место не меняет награду. В PoC список строится из подготовленных синтетических профилей-друзей.

**Титул коллекции:** короткая подпись, которую пишет языковая модель по составу собранных предметов. Валидатор отклоняет цифры, деньги, скидки и обещания, ограничивает титул тремя словами и 28 символами; при недоступности модели или нарушении контракта показывается детерминированный шаблон.

**Реферальный сценарий `family_relay`:** после основной интеграции приглашённый выполняет первое подтверждённое квалифицирующее покупочное действие. Пригласивший получает один заранее обещанный обычный цифровой предмет существующего каталога, полезный для его рецепта. Это отдельное начисление с резервом будущей скидки. За регистрацию, ссылку, открытие коробки или обмен бонус не выдаётся. Одного приглашённого нельзя зачесть двум пригласившим; первый реферальный бонус выдаётся один раз. Условия «нового участника», окно и частотный лимит пригласившего обязательны в конфигурации кампании до обещания, а не выбираются постфактум.

В расчёте реферала проверяются совместные затраты: первый товар и предмет приглашённого, предмет пригласившего, будущие скидки, проверка и риск. Например, синтетическое событие приглашённого В может выдать пригласившему А один `club-toaster`; повтор события не добавит вторую копию. Общий телефон не является самостоятельным отказом. Обмен дубликатами остаётся первым сценарием торговли предметами и не подменяет этот расчёт; демонстрационный расчёт реферала не ждёт реализации обмена.

## 6. Экономика и два источника финансирования

Все решения считаются на уровне **SKU**, а не по средней марже категории. Нужны закупочная стоимость, цена и маржа после обычных промо, наличие, поставщик, условия субсидии, история погашений и возвратов. Розничная цена подарка не равна расходу X5.

| Гипотеза | Условие допуска |
| --- | --- |
| Бренд финансирует товар и участвует в Ads-аукционе | Подтверждённое покрытие товара учитывается отдельно от рекламной ставки; полезность, прирост, риск и общий положительный результат обязательны |
| Товар финансирует X5 | Ожидаемая дополнительная маржа полностью покрывает товар, будущую скидку, фрод и операционные расходы |

Экономический контракт на фиксированном горизонте:

```text
ожидаемая дополнительная маржа следующих визитов
+ ожидаемая маржа последующих платных повторных покупок
+ ожидаемая рекламная выручка
+ ожидаемая субсидия поставщика
− ожидаемая стоимость бесплатного товара для X5
− ожидаемая стоимость будущей скидки
− ожидаемые потери от фрода
− дополнительные операционные расходы
> 0
```

Две строки маржи должны охватывать непересекающиеся покупки: если платный повтор уже входит в маржу визита, второй раз его не прибавляем. Маржа здесь считается до новой игровой скидки; если скидка уже вычтена в исходной марже, отдельного второго вычета нет. Субсидия учитывается один раз: либо валовая стоимость минус субсидия, либо непокрытая стоимость без повторного прибавления субсидии.

В ранжировании используются ожидания с консервативными допущениями. **До показа** резервируется полная максимальная стоимость обещанного физического товара и будущей скидки. Свободный бюджет равен лимиту минус уже списанные расходы и максимальные непогашенные обязательства. Нельзя заменить такой резерв вероятностью погашения.

Процентный потолок скидки без ограничения суммы покупки не задаёт максимальный расход в рублях. До реальной выдачи требуется лимит рублёвой выгоды или базы скидки, список применимых SKU, срок и правила совместимости с промо. Пока их нет, hard budget для реального купона не доказан. При выдаче предмета учитывается добавляемая им ответственность за будущий рецепт; при создании купона резерв переносится без двойного учёта.

Для PoC выбран **единый купонный фонд**: общий рублёвый максимум любого купона — **100 ₽**, обеспечение каждого непотраченного или обещанного, но ещё не выданного цифрового экземпляра — **25 ₽**. Обещание и его выданный экземпляр считаются одной позицией; зарезервированный для обмена предмет также входит в непотраченные. Четыре копии атомарно расходуются на один купон: их 100 ₽ переходят в резерв этого купона без дополнительного расхода или освобождения. При обмене число копий и общий резерв сохраняются, хотя ожидаемая стоимость погашения может измениться. Уже созданные непогашенные купоны обеспечиваются отдельно своим зафиксированным максимумом, а потраченные на них копии исключаются из счёта.

Граница обеспечения: из N непотраченных и обещанных копий можно создать не больше ⌊N / 4⌋ купонов; резерв 25 × N не меньше 100 × ⌊N / 4⌋. Поэтому встреча предметов у одного владельца не требуется для финансового покрытия общим фондом. Полный купонный резерв равен 25 × N плюс сумма максимумов уже созданных непогашенных купонов. Персональный PoC исполняет это правило в браузерном снимке: предмет из коробки за входы попадает в общий инвентарь и удерживает те же 25 ₽ резерва, что и награда за задание.

Условие применимости — единый источник обеспечения всех купонов PoC и общий предел 100 ₽. Бюджеты разных брендов на товар и CPA не взаимозаменяемы с ним. Перед каждым новым обещанием проверяется доступность средств в соответствующем фонде; повышение лимита старых купонов или предметов требует дополнительного обеспечения. Реальные пределы, ассортимент и сочетание промо согласуются с X5 перед пилотом.

Финансирование не отменяет уже данное обещание. При невозможности обеспечить бюджет или наличие новое задание не показывается. Закрытие кампании не освобождает от ранее зарезервированных наград.

### Экономика повторной товарной цели

Два источника финансирования действуют и для повторных целей: обеспеченное финансирование брендом либо X5 при положительной консервативной дополнительной марже после всех расходов. Бесплатный товар не обязательно дороже процентной скидки: сравниваются закупочная стоимость конкретного SKU и стоимость погашения купона, а не розничная цена подарка и номинальный процент.

До показа товарной цели резервируются полная стоимость одного обещанного SKU и его доступность на период исполнения. Резервы будущих купонов на цифровых экземплярах сохраняются отдельно: пользователь может потратить их на обычную скидку. При завершении **товарной** цели четыре копии списываются, их купонные резервы освобождаются, а резерв SKU переносится на выданное право без повторного списания. При обычном крафте четыре резерва превращаются в один купонный; резерв активной товарной цели остаётся до её исполнения, явного отказа или истечения срока. Резерв — обеспечение обязательства, а не второй расход.

Синтетическая иллюстрация жёсткого резерва: четыре цифровые копии по 25 ₽ и активная цель с себестоимостью SKU 25 ₽ требуют 100 + 25 = **125 ₽** открытого обеспечения. После выбора товарного результата купонные 100 ₽ освобождаются, 25 ₽ продолжают обеспечивать получение товара. Уже обещанный первый подарок, если он ещё не исполнен, учитывается дополнительно. Это не цена X5 и не доказательство прибыльности.

Ожидаемая стоимость учитывает альтернативные пути выбора: один набор не приносит одновременно товар и купон. Если пользователь создаёт купон, а затем собирает новые копии для товара, это разные расходы и обязательства. Допуск проверяет экономику всего оставшегося пути: будущие цифровые начисления, все физические награды, купоны, фрод и операции; одну дополнительную покупку нельзя приписать нескольким целям. Уже накопленные или полученные обменом копии могут завершить рецепт без нового визита — за них нельзя автоматически приписывать дополнительную маржу. Исчерпание бюджета прекращает новые обещания, сохраняя прежние.

### Расчёт коробок за вход и купонов — 07.09.2026

Один предмет требует 25 ₽ обеспечения; четыре предмета дают купон по прежней формуле 5–17%, максимум 100 ₽. При сумме подходящих товаров 500 ₽ это 25–85 ₽ фактической скидки, а не гарантированные 100 ₽. Старые купоны сохраняют максимум 10 ₽.

| За 28 дней на одного участника | Полное купонное обеспечение |
| --- | ---: |
| 28 ежедневных коробок (отклонённый вариант) | 700 ₽ |
| Четыре коробки за входы | 100 ₽ |
| Четыре коробки за входы и четыре выполненных задания | 200 ₽ |

Сценарное допущение: из восьми предметов собраны два купона; 60% купонов погашаются на полные 100 ₽; операции стоят 10 ₽ на участника, дополнительные потери составляют 2% выплат. Расход — 2 × 100 × 0,6 × 1,02 + 10 = **132,40 ₽ за 28 дней**. При чистом дополнительном доходе Ads 60 ₽ остаётся покрыть **72,40 ₽ дополнительной маржи**. При условных 75 ₽ на действительно дополнительную покупку это 0,97 покупки на участника. Без Ads — 1,77. При полном погашении расход достигает 214 ₽. Это арифметические сценарии, не измеренная экономика X5 и не оценка привычки.

Чистый доход Ads здесь уже очищен от расходов рекламного контура и покрытия первого подарка. Если подарок не покрыт, его полная себестоимость добавляется отдельно. Сам вход не является оплачиваемым CPA-событием. Обычные покупки, которые произошли бы без игры, не создают дополнительную маржу. Резерв нужен на полный максимум даже при прогнозе погашения 60%; непогашенные права не освобождаются автоматически.

При пустом инвентаре первый физический товар себестоимостью 25 ₽ плюс один предмет требуют 50 ₽ обеспечения. Четыре предмета плюс такой товар — 125 ₽; отдельная начатая коробка добавляет ещё 25 ₽. Для тысячи участников с четырьмя входными и четырьмя покупочными предметами нужен купонный фонд 200 000 ₽, физические подарки и операции обеспечиваются отдельно. Текущий пример фонда 10 000 ₽ не увеличен: он обеспечивает такой объём лишь для 50 участников, при отсутствии прежних обязательств. Профили браузерного демо изолированы; это не общий защищённый бюджет пилота.

## 8. Техническое решение

### 8.1. Текущий и целевой контуры

Текущее веб-демо использует React, TypeScript и Vite. Игровые правила живут в существующих модулях `webapp/src/features/home/`; второй каталог предметов для рекомендаций не создаётся. В репозитории есть backend-шаблон на Hono и Prisma, но он не обслуживает игровую выдачу.

Целевая архитектура: **синтетическая история и кампании → признаки и допустимые кандидаты → RecSys → проверка экономики/риска и Ads → резерв и решение → объяснение → существующая игра → журнал событий**. Это логические части одного продукта, не повод вводить микросервисы.

Runtime RecSys и offline learned-контур написаны на Python standard library; новые зависимости не добавлялись. Для защищённой выдачи, биллинга и атомарного обмена требуется серверный слой и транзакционное хранение в рамках существующей архитектуры. Реальные кассы, CRM, платёжные списания и промышленная нагрузка не нужны для хакатонного PoC.

### 8.2. Персонализация: next-best-action recommender

Входы: покупки категорий и SKU, ритм и давность визитов, история заданий, инвентарь, недостающие предметы рецептов, доступные кампании, наличие, маржа и риск. Каталог кандидатов небольшой, поэтому оцениваем его целиком; two-tower retrieval не нужен.

Первая версия — объяснимые правила: знакомые категории, достижимость задания в привычном ритме, прогресс нужного рецепта, частотные лимиты, стоимость и отказ от неподходящих вариантов. Она подключена к отдельной панели локального PoC через Vite middleware и Python CLI.

Порядок baseline фиксируется так, чтобы его можно было воспроизвести и проверить:

1. Собрать кандидаты «действие + окно + предмет + рецепт + допустимая физическая награда» из существующего каталога. Исключить недоступные и чувствительные товары, нарушенные лимиты, неопределённые условия и риск выше допуска.
2. Проверить выполнимость по привычному ритму. Первый челлендж — один покупочный день, без искусственного увеличения чека. Для новой категории нужны близость к знакомой и отдельный лимит исследования.
3. Оценить продвижение рецепта: увеличивает ли обещанный ID число разных подходящих предметов и позволяет ли собрать четыре копии. У пользователя без предметов сначала полезная безопасная категория, затем старт выбранного рецепта.
4. Проверить консервативную дополнительную экономику и полный резерв. До экспериментальных логов значения дополнительного эффекта — явно заданные сценарные допущения, а не доказанный uplift.
5. Выбрать обычное допустимое действие и сравнить допустимые пары «действие + кампания» в Ads-контуре. Ставка не может пропустить нерелевантное или убыточное действие. Вернуть один челлендж с причиной выбора, отказами альтернатив и версией правил.

Точные сортировки и будущие поля кандидата заданы в [плане RecSys](../../recsys/PLAN.md). Для одинаковых входов и версии правил получается одинаковый baseline. Пример: три разных обычных предмета завтрака → `breakfast-pan` → четыре разных совпадения → 8%; другой безопасный профиль может получить другой предмет, а отрицательная экономика приводит к отказу до показа.

Для повторного цикла кандидат связан с выбранной товарной целью или обычным рецептом скидки. RecSys рекомендует посильный путь к известной награде; уже обещанный SKU не заменяется из-за нового ранжирования. Цель, её стоимость, окно, прогресс и оставшиеся условия входят в снимок до решения. Вероятность забрать бесплатный товар не подменяет вероятность последующей платной покупки или её дополнительный эффект.

Offline PoC уже реализует T-learner-подобный контур на рандомизированных синтетических логах:

- отдельные `LogisticRegression` оценивают вероятность квалифицирующего визита с заданием и без задания;
- разность прогнозов — оценка дополнительного эффекта; высокая вероятность покупки сама по себе не означает прирост;
- `IsotonicRegression` калибрует uplift-разность на отдельной calibration-выборке;
- отдельная модель оценивает вероятность подтверждённого рекламного события.

Реализация разделяет 6 000 синтетических пользователей на train/calibration/test, использует только предрешенческие признаки и сравнивает политики на одинаковой held-out выборке. На 1 215 test-пользователях learned profit-gated политика дала +18 665,20 ₽ против +13 533,60 ₽ rules и −6 790,60 ₽ fixed dairy; calibrated uplift RMSE — 0,063689, billable AUC — 0,801916. На пяти seed learned выше rules и положителен: +15 828,20…+19 431,60 ₽, среднее +17 763,76 ₽. Это синтетическое доказательство работоспособности процедуры. Реальное обучение требует рандомизированного воздействия/контроля с одинаковым определением исхода и созревшим окном; одна пара моделей оценивает только согласованный treatment.

Отсутствие покупок категории — повод для ограниченного исследования, а не доказательство интереса. Новый товар допускается при близости к знакомым категориям, безопасности и положительной ожидаемой экономике. Вероятность исследования логируется только при фактической рандомизации.

Факт закрытия тематического рецепта обновляет будущий прогресс аватара при любом из двух результатов, без двойного зачёта.

### 8.4. Ads: один плейсмент и закрытый first-price CPA-аукцион

Бренды конкурируют за финансирование одного подходящего челленджа. Ставка задаётся брендом; модель её не предсказывает.

В локальном PoC аукцион исполняется на каждом новом решении. В dairy и coffee есть минимум по две конкурирующие кампании. До score проверяются категория, период, доступный бюджет с учётом резервов, частотный лимит за 14 дней, минимальное качество и ожидаемый прирост; risk и stock уже проверены кандидатом задания. Для первого подарка сумма `bid + subsidy` должна полностью покрывать себестоимость физического SKU; 25 ₽ резерва цифрового предмета обеспечивает отдельный купонный фонд. Score использует ожидаемую first-price оплату, качество, billable probability, маржу X5, pacing и непокрытую стоимость награды. Pacing влияет только на allocation. При публикации в глобальном браузерном ledger резервируются ставка и субсидия; свежее квалифицированное `allow`-событие создаёт одно списание, повтор — ни одного.

Кампания может обеспечивать конкретный товар повторной цели. Это не второй рекламный плейсмент и не обещание финансирования будущими ещё не состоявшимися торгами: средства и наличие нужны до показа цели. Следующие задания не меняют её SKU и источник уже обеспеченного обязательства. Получение бесплатного товара само по себе не создаёт дополнительный CPA-платёж; оплачиваемое событие закреплено отдельно.

1. Убираем кампании без релевантности, наличия, допустимой частоты, бюджета, приемлемого риска и минимального ожидаемого прироста.
2. Проверяем положительную ожидаемую экономику и возможность полного резерва обещания.
3. Оставшихся ранжируем по ожидаемой оплате бренда, дополнительной марже X5, темпу расходования бюджета и непокрытой стоимости награды, включая будущую скидку.
4. Победитель платит **свою исходную ставку** один раз после подтверждения согласованного события.
5. В первом runtime-цикле без рекламного победителя физический подарок не показывается и возвращается `no_action`; после него возможен органический цифровой челлендж. Если полезного задания нет вообще — `no_action`.

Кампания заранее определяет, что оплачивается: подтверждённая покупка товара, trial или платный повтор, с окном атрибуции и правилами возврата. Клик, открытие коробки и любой визит не подменяют этот исход. Вероятность рекламного события и прирост покупочных дней X5 — разные величины. Даже при incrementality gate нельзя утверждать, что конкретный визит точно не произошёл бы без рекламы.

Pacing меняет приоритет участия кампании, **не договорную цену** и не знак экономического допуска. Для жёсткого рекламного бюджета резервируется максимум возможного платежа по выданному обязательству; ожидаемая оплата используется для прогноза. Финансирование награды и CPA-бюджет учитываются раздельно.

Локальный биллинг уже обеспечивает максимум одно списание исходной ставки на задание после подтверждённого события; дубликат не создаёт второй платёж. Полная обработка возвратов остаётся production-задачей: только утрата квалифицирующего условия отменяет оплату до списания либо создаёт отдельную кредитовую корректировку после списания со ссылкой на исходный платёж. Возврат постороннего товара не отменяет сохранившееся условие. Рекламная корректировка сама по себе не удаляет пользовательскую награду: право на неё и риск разбираются по условиям задания.

Подход к отбору по качеству соответствует общей отраслевой практике: Google Ads учитывает ставку, качество, контекст и пороги. Это аналог принципа, а не утверждение, что Google использует нашу модель first-price CPA. [Google Ads Help](https://support.google.com/google-ads/answer/6366577?hl=en-GB)

Расширенная аналитическая проверка сравнивает highest-bid, quality-adjusted, profit-aware и incrementality-gated политики при одинаковых бюджетах и данных. Такое сравнение раскрывает Ads/RecSys-компромиссы; выполнение всех четырёх политик не является обязательной частью ближайшего демо. Заведомо слабые политики допускаются только как синтетические сравнения, а не как способ выдавать реальные необеспеченные награды.

### 8.5. Роль LLM и объяснение

LLM используется как ограниченный генератор заголовка карточки после выбора допустимого задания и расчёта резерва. Локальный адаптер вызывает Qwen3 1.7B через Ollama; при отсутствии модели, ошибке или таймауте возвращается детерминированный шаблон. RecSys определяет следующий шаг, а фактические условия формирует система.

Для карточки задания вход — выбранное решение, рецепт, недостающий предмет и уже утверждённые условия награды. Сырые чеки и идентифицирующие данные модели не передаются. В текущем PoC модель предлагает короткий заголовок задания, а отдельно по агрегированному составу собранных предметов — титул коллекции. Тело карточки, условие, срок, цифровая и физическая награды и пометка спонсора собираются детерминированно из решения и проходят проверку контракта.

Пример для подготовленного инвентаря: «Доброе утро: Сковорода завтрака». Точные условия покупки, товар, срок и спонсорство интерфейс выводит из проверенных полей. LLM не создаёт финансовые обязательства, не меняет SKU или дедлайн, не снимает удержание и не скрывает спонсора. Живой локальный ответ принят валидатором 05.09.2026; это техническая проверка интеграции, а не доказательство пользы текста.

Пользу LLM проверяем сравнением с фиксированным шаблоном того же задания: понимает ли пользователь следующий шаг и связь предмета с целью. Дополнительно измеряем долю нарушений и замен шаблоном, задержку и стоимость генерации. Эти измерения ещё не проведены.

Основной провайдер локального демо — Ollama с Qwen3 1.7B; YandexGPT сохранён как необязательный HTTP-адаптер. Источник `llm` или `fallback` виден в диагностике. Название `QuestRank` в старых файлах — историческая метка внутреннего решения, не отдельный общеизвестный алгоритм; на защите используем термин next-best-action recommender.

### 9.2. Проверка реального эффекта

Основная метрика — дополнительные покупочные дни за 28 дней на назначенного участника относительно контроля. Также фиксируется доля пользователей с не менее чем N покупками за период, где N определяется до запуска. Защитная метрика — маржа на участника после бесплатных товаров, скидок, фрода и дополнительных операций.

Платный повтор категории считается после окончания заранее заданного окна поощрений, включая повторные товарные цели; получение самого подарка не входит в повтор. Для проверки устойчивости отдельно задаётся общий для назначенных групп период без новых целевых подарков и дополнительных игровых скидок, с сохранением ранее выданных прав и сопоставимых обычных промо. Начало наблюдения не привязывается только к дате фактического получения подарка успешными участниками. Дополнительно измеряем стоимость дополнительного покупочного дня, возвраты, удержания, погашения и понимание условий.

Разделяем проверки:

| Сравнение | Какой вопрос проверяет |
| --- | --- |
| Игра против такого же задания и награды без коллекции | Добавляет ли игра пользу сверх промо при сопоставимых условиях и бюджете |
| Персональный выбор против одного сильного фиксированного задания | Даёт ли RecSys преимущество перед простой хорошей механикой |
| Отдельная группа без бесплатного физического товара | Какую часть эффекта и расходов создаёт первый подарок |
| Воздействие против контроля | Есть ли дополнительная частота и положительный итог для X5 |

В сравнении игры с обычным предложением одинаковы конкретный товар или купон, доступный выбор награды, требования к покупкам, сроки и финансовый бюджет. Больший подарок в игровой группе не является доказательством пользы коллекции. Отдельно измеряются понимание цели и желание получить результат, эффект игры при равной награде и сохранение платных покупок после поощрений; эти три вывода не подменяют друг друга.

Результат считается по всем назначенным участникам — включая отказавшихся, не завершивших задание и получивших `no_action`. Для обмена/рефералов учитывается взаимное влияние: единица рандомизации — домохозяйство или иной заранее определённый кластер; обмен между группами ограничивается либо явно учитывается в дизайне. Сравнение только получивших подарок создаёт смещение.

Reward fading необязателен и сам по себе не отделяет игру от скидки. После награды сохраняем окно наблюдения за платными покупками. Доход бренда, факт CPA-события и дополнительная маржа X5 анализируются отдельно.

Шкала организаторов: 0 — не раскрыто; 1 — существенные пробелы; 2 — основное раскрыто с вопросами; 3 — выводы подтверждены фактами, тестами или демонстрацией. Максимум — 15. Таблица ниже — требования к доказательствам, не выставленные себе баллы.

| Критерий | Что защищаем | Что нужно предъявить |
| --- | --- | --- |
| Соответствие кейсу | Короткий путь до ценной награды и персональная игра между покупками | Выбранный сегмент, один следующий шаг; явное покрытие требований и оставшихся пробелов |

Исходный кейс также перечисляет обновление аватара/рейтинга, реферальный расчёт, симуляцию и одностраничный план проверки. В локальном PoC аватар считает уникальные рецепты, рейтинг сравнивает друзей по собранным наборам и предметам, а реферальный расчёт однократно выдаёт обеспеченный обычный предмет на синтетическом событии. Связь Ани и Бориса и статус награды показаны на вкладке «Друзья»; отправка реального приглашения не подключена.

Сейчас самый сильный предъявляемый результат — связанный локальный путь от синтетической истории через Ads-аукцион до задания, проверенной карточки, тестового чека, однократных биллинга и выдачи двух обещанных результатов, обмена и существующего крафта. Следующий шаг к защите — проверить понятность и желанность на 5–7 людях, подтвердить рубрику человеком и отрепетировать показ. Реальные кассы, промышленный антифрод, production serving модели и инфраструктура рекламодателей в PoC не входят.

Обязательные отрицательные сценарии следующего PoC: повтор чека; два чека одного дня; возврат до и после CPA; закрытие кампании и отсутствие SKU после обещания; два одновременных подтверждения обмена; попытка потратить зарезервированный предмет; легитимная семья с общим устройством; дорогая награда при слабом приросте; `no_fill` с допустимым обычным заданием и `no_action` без нового обещания.

### Данные и параметры, без которых нельзя выдавать реальные награды

| Что задаётся до запуска кампании | Кто подтверждает | Что происходит при отсутствии |
| --- | --- | --- |
| SKU/упаковка, закупочная стоимость, маржа, применимые товары и доступность | X5 / товарный каталог | Товар не участвует в подборе |
| Обеспеченная субсидия, исходная CPA-ставка, оплачиваемое событие, окно и возврат | X5 и бренд | Нет спонсорской кампании; обычное задание проходит собственный допуск |
| Рублёвый лимит купона, срок, совместимость с промо, место/срок получения SKU | Продукт и экономика X5 | Нельзя зарезервировать и показать реальное обещание |

Это внешние входные данные и необходимые настройки, а не незавершённый выбор игровой механики. В демонстрации они могут быть заданы синтетически и подписаны соответствующим образом. Производственные значения и коммерческие договорённости не выдумываются.

## Приложение А. Полный каталог и спецификация игры

Этот документ подробно описывает **действующую игру коллег**: коробка → цифровой предмет → инвентарь → четыре предмета → собственная скидка → демонстрационный штрихкод. Каталог и расчёт уже используются веб-прототипом. В том же локальном интерфейсе подключены покупочное задание, обещанный предмет, демонстрационное право на товар и обмен доступными предметами одинаковой редкости. Реальная товарная выдача и защищённый серверный учёт остаются следующей интеграцией.

Источник фактического поведения — игровые модули, перечисленные в конце документа. Общее решение, экономика и правила будущих слоёв зафиксированы в [описании проекта](project-description.md) и [продуктовых материалах](product-materials.md).

![Все 24 предмета, сгруппированные по редкости](item-pool-preview.webp)

### А.1. Что представляет собой предмет

Предмет — цифровая игровая копия из каталога, которую можно положить в одну из четырёх ячеек создания скидки. Изображение тостера или холодильника не означает выдачу физического прибора. Физический товар за первый челлендж — отдельная награда.

У каждого вида предмета есть стабильный ID, название, редкость, категория, игровой текст и иконка. Один вид может храниться в нескольких копиях. Обычная копия даёт 1 очко силы, эпическая — 2, легендарная — 3.

Категория предмета используется для смешанной скидки, когда тематического рецепта недостаточно. У собранного рецепта собственная категория. Эти подписи пока являются демонстрационными категориями: связка с конкретными кассовыми SKU не подключена. Например, название «Любимые покупки» у Волшебного холодильника само по себе не означает, что состав этой категории уже персонализируется.

#### Где пользователь видит информацию

| Экран | Что показывает |
| --- | --- |
| Получение из коробки | Иконку, название, редкость и прямое название категории |
| Сетка инвентаря | Иконку, визуальную редкость и количество доступных копий относительно общего количества |
| Карточка предмета | Крупную иконку, название, редкость и игровой намёк; прямую категорию в этой карточке не показывает |
| Незавершённая комбинация | Ближайший рецепт, число совпадений и иконки подходящих предметов |
| Четыре заполненные ячейки | Название будущей скидки, категорию, силу, бонус и итоговый процент |
| Созданная скидка | Итоговую категорию, процент, редкость и четыре использованные копии |

Таким образом, игровая загадка относится к карточке инвентаря. Категория раскрывается на других этапах взаимодействия.

### А.3. Коробка и получение предмета

#### Сценарий действующего демо

1. Пользователь заходит в профиль в три разных дня. После третьего дня нажимает на готовую коробку.
2. В открывшемся экране зажимает коробку и двигает пальцем или мышью по экрану.
3. После достаточного движения начинается анимация открытия.
4. Через 1,4 секунды выбирается случайный предмет и автоматически добавляется в инвентарь.
5. Пользователь видит результат и нажимает «Забрать», чтобы закрыть экран. Начисление уже состоялось до этого нажатия.
6. Следующая коробка требует ещё три разных дня; день получения не засчитывается повторно. Лимит — четыре получения за последние 28 дней.

Жест использует координаты указателя, а не датчики движения телефона. Для открытия накапливается 620 пикселей перемещения; один сегмент даёт не более 90 пикселей. Отпускание пальца прекращает текущее движение, но не обнуляет накопленный прогресс этого открытия.

В интерфейсе показаны «За возвращение», три отметки дней, счётчик получений «из 4» и подсказка о сохранении прогресса. На третьем дне статус становится «Готова». Старый таймер больше не используется. В демо-стенде есть кнопка «Следующий день входа (демо)»: она меняет только день коробки, не время чеков и кампаний.

#### Вероятности

Каждое открытие сначала выбирает редкость, затем равномерно один из восьми предметов этой редкости.

| Редкость | Вероятность редкости | Предметов | Вероятность конкретного предмета |
| --- | ---: | ---: | ---: |
| Обычная | 70% | 8 | 8,75% |
| Эпическая | 25% | 8 | 3,125% |
| Легендарная | 5% | 8 | 0,625% |

Используется локальный случайный выбор. История покупок, уже имеющиеся предметы и незавершённые рецепты сейчас на него не влияют. Нет исключения повторов, гарантии легендарного предмета после серии открытий или гарантированного нового предмета. Один и тот же предмет может выпасть несколько раз подряд.

| Купите 3 готовых блюда «Рестория» | 1 из 3 | Одна коробка |
| Купите овощи или фрукты 3 раза | 2 из 3 | Одна коробка |
| Купите молочные продукты 2 раза | 0 из 2 | Одна коробка |

Карточки объединены заголовком «Задания недели» и отметкой «7 дней». Покупочные события не обновляют этот прогресс и не выдают коробки: связь с чеком относится к следующей интеграции.

### А.4. Инвентарь и четыре ячейки

#### Количество и хранение

Инвентарь хранит пары `itemId` и `quantity`. Первое получение создаёт позицию с одной копией; повтор увеличивает её количество. Дубликат не занимает отдельную клетку сетки.

Счётчик вида «5/24» означает пять разных видов предметов, **сейчас имеющихся в инвентаре**. Это не число всех копий и не история когда-либо собранной коллекции. Если последняя копия вида потрачена, позиция исчезает и счётчик уменьшается. Сетка показывает минимум восемь клеток и расширяется при росте количества разных предметов.

Инвентарь сохраняется в `localStorage` браузера с версией формата 1. При восстановлении:

- отсутствующая запись, неверный JSON или неподдерживаемая версия дают пустой инвентарь;
- неизвестный ID, нецелое, нулевое или отрицательное количество пропускаются;
- несколько сохранённых записей одного ID объединяются суммированием.

Это проверка формата локальных данных. Серверной проверки владения копиями, синхронизации между устройствами и защиты от ручной подмены количества пока нет.

#### Выбор и отмена

Ровно четыре слота используются для создания одной скидки. Заполнить их можно двумя способами: перетащить предмет мышью или пальцем; либо открыть его карточку, нажать «Выбрать предмет» и затем нажать на слот.

На каждой позиции инвентаря показано **доступно / всего**. Если из трёх копий одна помещена в слот, остаётся «2/3». Размещение временно уменьшает доступность внутри текущего экрана, но ещё не списывает предмет из сохранённого инвентаря.

| Действие | Поведение |
| --- | --- |
| Положить имеющуюся копию в пустой слот | Слот заполняется, доступность уменьшается на одну |
| Нажать на заполненный слот без выбранного предмета | Слот очищается, копия снова доступна |
| Поместить другой доступный предмет в заполненный слот | Содержимое заменяется, предыдущая копия освобождается |
| Повторно поместить тот же ID в тот же слот | Ничего не меняется |
| Попытаться использовать больше копий, чем есть | Размещение не выполняется; функция окончательного списания также отклоняет нехватку |
| Нажать на предмет, все копии которого уже размещены | Карточку можно посмотреть; кнопка выбора недоступна |
| Заполнить меньше четырёх слотов | Кнопка создания недоступна и сообщает, сколько копий добавить |
| Создать скидку из четырёх слотов | По одной копии каждого слота расходуется; слоты очищаются |

Повтор одного ID в разных слотах допустим при достаточном количестве копий. Например, две копии тостера требуют количества не менее двух. Незавершённые слоты хранятся только в состоянии экрана и не являются долговечным серверным резервом.

### А.5. Все семь рецептов

Рецепт — список подходящих видов предметов, а не единственная фиксированная четвёрка. Для бонуса достаточно трёх разных совпадений; четыре разных совпадения усиливают бонус. Четвёртый предмет в наборе с тремя совпадениями может относиться к другой теме.

| Порядок и ID | Рецепт | Категория результата | Полный состав подходящих предметов |
| --- | --- | --- | --- |
| 1. `breakfast` | Доброе утро | Завтраки, выпечка и горячие напитки | Клубный тостер; Молочный кувшин; Термокружка; Сковорода завтрака; Кофемашина бариста; Фартук пекаря; Фруктовая корзинка |
| 2. `fresh` | Свежий выбор | Овощи, фрукты и полезные продукты | Фруктовая корзинка; Овощной ящик; Блендер здоровья; Купол свежести; Молочный кувшин; Сковорода завтрака |
| 3. `movie` | Вечер без готовки | Снеки, напитки и готовая еда | Миска для снеков; Печь пиццайоло; Холодильник для пикника; Пресс идеального сэндвича; Морозильная камера |
| 4. `asian` | Азиатский ужин | Рыба, рис, лапша и азиатские соусы | Набор сушиста; Драконий вок; Королевский казан; Нож шефа; Овощной ящик; Сундук запасов |
| 5. `chef` | Ужин шефа | Мясо, свежие продукты и кулинария | Нож шефа; Гриль мастера; Золотой колпак повара; Овощной ящик; Волшебный холодильник; Королевский казан |
| 6. `dessert` | Сладкая пауза | Десерты, кофе и всё для выпечки | Фартук пекаря; Кофемашина бариста; Кристальная мороженица; Молочный кувшин; Фруктовая корзинка; Термокружка |
| 7. `pantry` | Домашний запас | Бакалея, заморозка и продукты долгого хранения | Сундук запасов; Морозильная камера; Волшебный холодильник; Холодильник для пикника; Клубный тостер; Пресс идеального сэндвича |

Один предмет может подходить нескольким рецептам. Для результата выбирается рецепт с наибольшим числом **разных ID**, совпавших с выбранными слотами. При равенстве побеждает первый по порядку таблицы: «Доброе утро», затем «Свежий выбор» и далее.

#### Подсказка ближайшего рецепта

При пустых слотах интерфейс предлагает Клубный тостер, Молочный кувшин и Термокружку. После первого выбора он находит ближайший рецепт по числу уникальных совпадений и предлагает ещё не выбранные предметы из списка этого рецепта в каталожном порядке.

Подсказка не проверяет наличие предложенных копий в инвентаре и не оптимизирует будущий процент или экономику. Покупочная история не участвует. Это действующая игровая подсказка; отдельный runtime RecSys решает задачу выбора полезного задания и награды в персональной панели.

### А.6. Точный расчёт скидки

#### Шаг 1. Сумма силы всех четырёх копий

Каждая копия учитывается независимо: обычная даёт 1, эпическая — 2, легендарная — 3. Поэтому сумма составляет от 4 до 12, даже если все четыре копии одинаковы.

| Сила набора | Базовая скидка |
| ---: | ---: |
| 4–5 | 5% |
| 6–7 | 7% |
| 8–9 | 10% |
| 10–11 | 13% |
| 12 | 15% |

#### Шаг 2. Один тематический бонус

| Разных совпадений с выбранным рецептом | Бонус |
| ---: | ---: |
| 0–2 | 0 процентных пунктов |
| 3 | +2 процентных пункта |
| 4 | +3 процентных пункта |

Дубликаты усиливают базу за счёт своей редкости, но для совпадений считаются одним видом. Бонусы нескольких рецептов не суммируются.

#### Шаг 3. Название, категория и итог

При трёх или четырёх уникальных совпадениях используются название и категория выбранного рецепта. При меньшем числе совпадений получается смешанный набор без бонуса: категория самого редкого выбранного предмета, название «Скидка на …». Если самых редких предметов несколько, действует первый в порядке слотов; перестановка такого смешанного набора может изменить категорию.

Итоговый процент — базовая скидка плюс тематический бонус, с программным потолком **18%**. В действующем каталоге достижимый максимум — **17%**: ни один рецепт не содержит четырёх разных легендарных предметов, которые одновременно дали бы 15% базы и 3 процентных пункта бонуса. Проверка всех 17 550 возможных наборов из четырёх копий с повторами подтверждает этот максимум.

Редкость готовой скидки рассчитывается отдельно от её процента:

| Сила набора | Редкость скидки |
| ---: | --- |
| 4–6 | Обычная |
| 7–9 | Эпическая |
| 10–12 | Легендарная |

#### Примеры, которые можно воспроизвести

| Четыре выбранные копии | Сила | Совпадения и бонус | Итог |
| --- | ---: | --- | --- |
| Клубный тостер + Молочный кувшин + Термокружка + Сковорода завтрака | 4 | Четыре разных в «Добром утре»: +3 п.п. | **8%**, «Доброе утро», обычная |
| Фруктовая корзинка + Овощной ящик + Блендер здоровья + Купол свежести | 7 | Четыре разных в «Свежем выборе»: +3 п.п. | **10%**, «Свежий выбор», эпическая |
| Золотой колпак повара ×2 + Волшебный холодильник + Королевский казан | 12 | Три разных в «Ужине шефа»: +2 п.п. | **17%**, «Ужин шефа», легендарная |
| Фруктовая корзинка ×4 | 4 | Один разный предмет: без бонуса | **5%** на фрукты, обычная |

Редкий предмет полезен для силы, а разнообразие — для тематического бонуса. Эти два свойства создают выбор: использовать имеющиеся копии сейчас или продолжить собирать нужную комбинацию.

### А.7. Результат, активная скидка и ограничения демо

После создания по одной копии каждого слота расходуется. Если количество вида становится нулевым, его позиция удаляется из инвентаря. Открывается результат с названием, процентом, категорией, редкостью, использованными предметами и бонусом.

Рядом с персонажем появляется значок активной скидки. Нажатие на него или на кнопку «Показать штрихкод» открывает EAN-13. Код имеет 13 цифр, корректную контрольную цифру и графическое кодирование; он формируется локально и не зарегистрирован в кассовой системе.

В браузере хранится **одна активная скидка**. Создание новой заменяет предыдущую без отдельного подтверждения; ранее потраченные предметы при этом не возвращаются. После перезагрузки активная скидка восстанавливается из отдельной записи `localStorage`.

| Область | Текущее поведение и граница готовности |
| --- | --- |
| Проверка сохранённой скидки | Проверяются формат, четыре известных ID, типы полей и контрольная цифра EAN-13; расчёт процента и категории по предметам заново не выполняется |
| Списание и выдача | Инвентарь и скидка записываются раздельно в браузере; единой защищённой серверной транзакции нет |
| Владение и синхронизация | Нет проверки владельца предметов и общей синхронизации между вкладками или устройствами |
| Ошибка хранения | Повреждённое содержимое обрабатывается при чтении; отдельное восстановление после отказа записи `localStorage` не реализовано |
| Погашение | Нет кассового подтверждения, одноразового серверного списания или гарантии глобальной уникальности кода |
| Условия скидки | Не подключены срок действия, рублёвый лимит, допустимая база покупки, точный состав SKU и правила сочетания с другими акциями |
| Экономия | Процент и демонстрационный штрихкод не подтверждают фактически сэкономленные рубли |
| Персонаж и рейтинг | Уровень равен числу уникальных завершённых рецептов 0–7; дружеский рейтинг сравнивает собранные наборы и предметы, а деньги остаются личной цифрой. Фартук пекаря и нож шефа можно надеть на маскота без влияния на скидку |
| Социальные действия | Локальный обмен 1:1 доступен по кнопке возле маскота: выбор предмета, демонстрационный QR, второй синтетический профиль, подтверждение, резерв и передача. Реального соединения устройств и серверного реестра нет |

Эти ограничения описывают фактический статус прототипа. Они не меняют согласованный целевой контракт: заработанные права и обещанные награды должны сохраняться.

### А.8. Подключение персонального PoC и будущий промышленный контракт

Локальный Python-движок использует снимок тех же 24 предметов и семи рецептов, выбирает одно допустимое задание и фиксирует обещанный ID **до показа задания**. После подтверждённого тестового события интерфейс показывает отдельное окно заранее назначенного предмета и добавляет его в общую коллекцию с теми же четырьмя слотами. Обычная коробка остаётся независимым способом случайного получения предмета с вероятностями 70/25/5, но оба источника пополняют один инвентарь.

После первого показанного, допустимого и выполненного челленджа пользователь получает также **один полный бесплатный физический SKU**. Это отдельное обязательство, а не обмен цифрового тостера на бытовую технику и не скидка вместо товара. Условия, конкретный товар, наличие и финансирование известны до показа.

Если инвентарь изначально пуст, первое задание даёт **один цифровой предмет из необходимых четырёх**. После подтверждения первого задания пользователь получает право на обещанный физический товар; сборка скидки требует дальнейших начислений. Демонстрация немедленного крафта должна явно использовать профиль с тремя ранее полученными копиями; скрытое стартовое начисление трёх предметов в продукте не предусмотрено.

Для интеграции необходимы:

- серверный учёт выдачи, владельца, доступного количества, резервов и списания с уникальными идентификаторами операций;
- сохранение версии каталога, рецепта и условий выданной скидки, чтобы изменения правил не меняли уже показанное обещание;
- полный резерв максимальных обязательств физической награды и будущей скидки до показа; цифровые предметы также могут увеличивать стоимость будущих погашений;
- атомарное создание скидки со списанием четырёх копий и проверкой текущего количества;
- прямой обмен любых имеющихся свободных предметов один к одному одинаковой редкости: можно отдать единственную копию; действуют 24 часа, подтверждение обеих сторон, резерв и атомарная передача, не более трёх завершённых обменов за неделю и минимум два подтверждённых покупочных дня у каждого участника;
- проверка дополнительной стоимости после обмена: равная редкость не означает одинаковую вероятность завершения рецепта и погашения скидки;
- точные SKU, срок, лимит суммы скидки, правила применения и одноразовое кассовое погашение, а также сохранение уже заработанных прав при отсутствии нового задания.

Физические товары, купоны, активные скидки и ещё не выданные награды не передаются. Обмен не начисляет отдельного бонуса. В повторных циклах конкретный бесплатный SKU может быть заранее показанной целью обеспеченного рецепта. Четыре копии используются на один результат — обычную скидку либо обещанный товар; за каждое задание товар не выдаётся.

Товарная цель не меняет существующую формулу: используются те же четыре доступные копии и тот же алгоритм выбора тематического рецепта с бонусом. Для получения SKU результат должен совпасть с рецептом активной обеспеченной цели. Четыре одинаковые копии не закрывают тематическую товарную цель. Сервер однократно списывает четыре экземпляра и создаёт право на конкретный товар; повтор запроса не выдаёт второй SKU и не создаёт купон на те же копии.

Первый подарок по заданию выдаётся отдельно и не требует крафта. Одновременно обещанные первый подарок и товар за рецепт — два обязательства. Для цели заранее резервируется полный SKU, отдельно сохраняются купонные резервы экземпляров. При выборе товара купонные резервы четырёх потраченных экземпляров освобождаются, резерв SKU переходит на право выдачи. Обычный крафт не отменяет цель автоматически. Наличие активного купона блокирует только новый купон, а не отдельное товарное право. Подробные состояния, сроки и исключения — раздел 4.4 [финального плана](project-description.md).

В локальном персональном PoC действует купонный фонд: максимум купона 100 ₽ и резерв 25 ₽ на непотраченный или обещанный цифровой экземпляр. Четыре копии сохраняют 100 ₽ резерва после крафта; при демонстрационном погашении резерв заменяется фактической экономией. Физическое право обеспечивается и списывается отдельно. Каждый синтетический профиль остаётся изолированным сценарием; общего серверного фонда между пользователями и реального товарного остатка пока нет.

Защищённый серверный реестр, POS, реальные товарные остатки и промышленная Ads-инфраструктура остаются следующей реализацией. Локальные Ads allocation, резерв и one-time billing уже работают в браузерном PoC. Полные правила финансирования, Ads, антифрода и приёмки: [описание проекта](project-description.md), [план RecSys/Ads](../../recsys/PLAN.md), [план работ](plan.md).
