# recsys: контракты, сценарии и план персонализации

Этот каталог содержит **фиксированные синтетические сценарии и локальные проверки**.
Работающий рекомендательный движок, обученные модели, рекламный аукцион и интеграция с игровыми
экранами здесь пока не реализованы.

Продуктовая спецификация — [описание проекта](../docs/project/project-description.md),
общая последовательность работ — [командный план](../docs/project/plan.md),
будущая техническая реализация — [PLAN.md](PLAN.md).

## Продукт, к которому подключаемся

**Коробка → цифровой предмет → инвентарь → четыре предмета → собственная скидка.**

Планируемый RecSys выбирает одно выполнимое задание по истории покупок и недостающим предметам
рецепта. После первого показанного, выполненного и подтверждённого допустимого задания
пользователь гарантированно получает обещанный бесплатный физический товар и полезный цифровой
предмет. Результат не подменяется случайным выпадением из демонстрационной коробки.

В следующих циклах основа — предметы, обмен дубликатами и создание скидок. Физический товар
предусмотрен только для редкого milestone или полностью профинансированной кампании.
Две гипотезы финансирования первого товара — бренд либо X5 при положительной ожидаемой
дополнительной марже после всех затрат. Обмен, бесплатный SKU, RecSys, Ads и антифрод пока
описаны как следующий шаг; текущий интерфейс использует игровые модули в `webapp`.

## Что означает текущий результат проверок

На текущем наборе мутационный тест обнаруживает 60 из 60 нарушений по 11 категориям,
не отклоняет ни один из 24 легитимных вариантов; 25 нарушенных вариантов исправляются,
35 заменяются шаблоном. Это результаты **конкретного детерминированного набора**.
Они не доказывают качество живого LLM-агента, релевантность персонализации, защиту от мошенников
или бизнес-эффект.

Каталог описывает использование LLM при подготовке кампаний. Вызов модели внутри продукта,
запускаемый генератор, обучение и измерение эффекта на пользователях здесь не представлены.
Для защиты использование ИИ командой нужно подтверждать фактическими инструментами,
примерами задач и проверенными результатами работы.

Все денежные значения, вероятности и эффекты в JSON синтетические. Один общий
`contribution_margin_rub` из каталога не заменяет маржу отдельных SKU.
`expected_liability` — прогноз ожидаемого расхода, а не резерв максимальных обязательств.
Существующие `effective_bid` и `pacing_multiplier` не задают будущую цену first-price списания:
победитель должен платить исходную договорную ставку.

## Следующая реализация

План — next-best-action recommender с полным перебором небольшого каталога кандидатов:
сначала правила; после появления рандомизированных логов — две `LogisticRegression`
для визита с заданием и без него, `IsotonicRegression` для калибровки и отдельная модель
подтверждённого рекламного события.

Ads — один плейсмент, закрытый quality-adjusted first-price CPA-аукцион с порогами
релевантности, инкрементальности, наличия, риска, частоты и бюджета.
До обещания резервируется полная максимальная стоимость товара и будущей скидки.
Обмен и серверный учёт наград требуют отдельного контракта и реализации.

Новые поля пока описываются только в [PLAN.md](PLAN.md). JSON-схема, кампании и фикстуры
сохраняют текущий формат. Их расширение и подключение к игре — отдельный согласованный этап.

## Локальная проверка

Из корня репозитория:

```bash
python3 recsys/validate.py
python3 recsys/validate_explanation.py
python3 recsys/eval_creatives.py
```

Проверки не требуют новых зависимостей. Они не запускают симуляцию на 1–10 тыс. пользователей
и не измеряют требуемую кейсом релевантность на 30–50 профилях: эти результаты ещё нужно получить.
